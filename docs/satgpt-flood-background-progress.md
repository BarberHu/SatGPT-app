# SatGPT Flood 项目背景与修改进度

> 创建时间：2026-03-18
> 维护方式：持续更新
> 当前范围：仅记录代码改造相关背景、目标、现状与进度，不包含培训材料、UX 测试执行与运维成本核算的详细实施内容

---

## 1. 项目背景

项目方为南京师范大学提供了一份针对 SatGPT Flood 方向的 TOR（Terms of Reference）。这份需求书不是单点功能修补，而是希望把当前 SatGPT 逐步收敛为两条更清晰的产品线：

1. `Basic Version`
   目标：面向基础洪水事件与淹没热点制图，强调稳定、直接、易上手。
2. `Advanced Version`
   目标：面向更完整的灾前-灾后分析、光学与雷达联合判读、快速影响评估，强调标准化流程与更强的分析能力。

从项目管理视角看，这份 TOR 混合了以下几类交付：

- 代码改造
- 文档与部署说明
- UX/UI 测试设计
- 培训与能力建设材料

当前阶段优先聚焦第一类，即：**代码改造与版本收敛**。

---

## 2. TOR 的代码相关目标

结合需求书，当前与代码直接相关的核心目标如下。

### 2.1 Basic Version（截止 3 月底）

- 更新 JRC Global Surface Water 数据及其他可用图层
- 增加 `asset uploading` 能力
- 改进单次洪水与淹没热点制图代码
- 修复 2025 至 2026 Q1 培训/调研中收集到的问题

### 2.2 Advanced Version（截止 4 月底）

- 开发基于光学与雷达数据的标准洪水范围制图代码
- 增加灾前/灾后影像分析关键功能
- 增加基于开源社会经济数据的快速洪水影响评估能力

---

## 3. 当前仓库现状判断

通过对仓库的初步摸底，当前项目并不是单一系统，而是两条能力线并存。

### 3.1 老版基础线

主要结构：

- `app.py`
- `frontend/src/components/ControlPanel.js`
- `frontend/src/hooks/useMapData.js`
- `frontend/src/services/api.js`

特点：

- 基于 Flask
- 前端存在传统 `Ask` 模式
- 依赖固定 fishnet 网格选区
- 已支持：
  - 单次淹没事件图层
  - 淹没热点图层
  - 部分基础辅助图层
  - GEE 代码下载

这条线很适合作为 `Basic Version` 的基础。

### 3.2 新版高级线

主要结构：

- `agent/server.py`
- `agent/gee_service.py`
- `agent/flood_agent.py`
- `frontend/src/components/AgentPanel.js`
- `frontend/src/services/agentApi.js`
- `runtime/server.ts`

特点：

- 基于 FastAPI + LangGraph + CopilotKit
- 已支持 Agent 工作流
- 已支持：
  - 灾前 / 峰值 / 灾后日期
  - Sentinel-1 / Sentinel-2 影像切换
  - 洪水检测图层
  - 人口 / 建成区 / 土地覆盖影响评估
  - GEE 代码导出

这条线很适合作为 `Advanced Version` 的基础。

---

## 4. 当前已确认的关键结论

### 4.1 Basic / Advanced 与现有代码的映射

当前最合理的工程映射为：

- `Basic Version` -> 以 Flask + Ask 模式 + 老版控制面板为主
- `Advanced Version` -> 以 FastAPI + Agent 模式 + AgentPanel 为主

这不是绝对真理，但在当前仓库结构下，这是 ROI 最高、改造成本最低的划分方式。

### 4.2 已有能力

当前项目已经具备以下可复用能力：

- 洪水相关图层展示
- Sentinel-1 / Sentinel-2 影像获取
- SAR 变化检测
- 基于 WorldPop / ESA WorldCover / GHSL 的影响评估
- Agent 驱动的事件识别与流程串联

### 4.3 明显缺口

当前明显缺少或不完整的能力：

- 真正的 `asset uploading`
  - 当前代码内部可以消费 `geojson`
  - 但前端没有完整的用户上传入口和上传工作流
- Basic 与 Advanced 两条线的产品边界还不够清晰
- 老版数据图层存在版本混用问题
- 高级版虽然已有后端能力，但还没有完全产品化为标准分析流程

## 5. 当前修改目标

本轮代码改造的目标不是“无限扩展功能”，而是先把版本边界收口。

### 5.1 Basic Version 目标

- 统一和升级基础版使用的数据图层版本
- 增加 AOI / 资产上传能力，至少支持 GeoJSON
- 保留 fishnet 选区，同时增加更灵活的区域输入方式
- 让基础版形成稳定闭环：

```text
选区/上传 AOI
  -> 请求图层
  -> 查看结果
  -> 导出 GEE 代码
```

### 5.2 Advanced Version 目标

- 把当前 Agent 版已有能力整理为标准分析流水线
- 强化灾前/灾后影像对比表达
- 完善光学 + 雷达联合分析的标准输出
- 强化 impact assessment 的结果展示与解释性

### 5.3 本轮优先纳入的基础性重构方案

当前判断，本轮不做“大拆大改”式重写，而是优先做两项高 ROI、直接服务后续需求落地的结构性重构。

#### 5.3.1 AOI 输入统一抽象

目标：

- 把当前分散在老版 fishnet 选区、`AoI_cords` 字符串、新版 `bounds`、新版 `geojson` 之间的区域输入方式，统一抽象为同一类 AOI 概念
- 明确“fishnet 只是 AOI 的一种来源，而不是 AOI 本体”
- 为后续 `asset uploading`、GeoJSON 上传、地图框选、地点解析生成边界等输入方式预留统一接入点

当前现状：

- 老版基础线主要使用 fishnet 点击结果 -> `selectedGridCords` -> `AoI_cords`
- 新版高级线已经支持 `geojson`、`bounds`、`longitude/latitude + buffer`
- 两条线虽然都在表达“分析区域”，但协议和传递方式不一致

重构收益：

- 降低新 AOI 输入方式接入成本，避免每新增一种输入都要分别适配基础线和高级线
- 让图层请求、影响评估、GEE 代码导出共享同一套区域语义
- 为 Basic Version 的“选区/上传 AOI -> 请求图层 -> 查看结果 -> 导出代码”闭环提供稳定底座

建议原则：

- 统一 AOI 的上位概念
- 允许多种输入来源
- 在接口层优先向标准化 AOI 结构归一，而不是继续扩散 `AoI_cords` 这种历史字段

#### 5.3.2 图层与数据源配置化

目标：

- 把当前散落在后端路由、Agent 服务、前端导出脚本中的图层数据源、版本号、可视化参数和适用版本收敛到统一配置
- 建立可读、可维护、可被代码直接消费的图层目录（layer catalog）

当前现状：

- 老版基础线存在 JRC 图层版本混用
- 前端 GEE 导出逻辑与后端图层实现存在口径漂移风险
- Basic / Advanced 各自使用哪些图层，目前主要体现在代码分支中，而不是集中定义

重构收益：

- 统一图层版本口径，减少“图能显示但结果解释不一致”的隐性风险
- 后续切换数据源版本时只改一处，不需要全仓库搜索硬编码
- 让前端展示、后端分析、GEE 导出围绕同一份图层配置工作
- 为 Basic / Advanced 的产品边界提供更清晰的工程表达

建议原则：

- 配置化的对象不只是“说明文档”，而应是代码可直接读取的配置
- 优先配置：图层名、数据源 ID、版本、可视化参数、适用产品线、默认可见性
- 业务流程代码负责“怎么跑”，图层配置负责“用什么数据跑”

## 7. 当前风险与注意事项

### 7.1 范围失控风险

TOR 把代码、部署、UX 测试、培训都混在一起。如果不先收敛范围，很容易导致：

- 任务边界失真
- 优先级混乱
- 截止日期前交付质量下降

因此当前默认策略是：

- 先做代码改造
- 文档和部署说明后续补齐
- 培训与 UX 测试方案单独拆分

### 7.2 `asset uploading` 的定义风险

需求书写的是 `asset uploading`，但这个词本身不够精确。它可能指：

- 上传 GeoJSON
- 上传 Shapefile
- 上传 KML
- 上传已有 GEE Asset ID

当前为了控制复杂度，建议第一阶段默认解释为：

- 支持上传 `GeoJSON`
- 后续再扩展到其他格式

### 7.3 数据版本一致性风险

当前仓库中不同模块存在图层版本混用。若不先统一，会导致：

- 图层口径不一致
- 前后端解释不一致
- 文档难以维护

---

## 8. 建议的下一步

建议按以下顺序推进：

1. 先细化 `Basic Version` 改造清单
2. 明确 AOI 输入统一抽象与 `asset uploading` 第一阶段的输入格式、交互方式
3. 明确图层与数据源配置化方案，先统一版本与口径
4. 再细化 `Advanced Version` 的标准工作流
5. 最后进入实际编码与验证

推荐原则：

- 先做闭环，不先做炫技
- 先做输入与流程统一，再做算法增强
- 先把 basic 稳住，再把 advanced 做强

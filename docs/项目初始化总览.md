## 1. 这个项目本质上是什么

`SatGPT-app` 不是一个单体网页，而是一个围绕“洪水事件分析”搭起来的多服务协作系统。

一句话概括：

**用大模型理解洪水事件，用 Google Earth Engine 做遥感计算，用 React + Mapbox 把结果可视化。**

如果用 FPS 游戏来类比：

| 类比对象 | 在项目中的对应物 |
|---|---|
| 玩家 HUD | `frontend/`，用户直接看到的界面与交互 |
| 联机中继服务器 | `runtime/`，把前端对话转发给 Agent |
| 战术指挥官 | `agent/`，理解问题、组织分析流程、调用 GEE |
| 老地图脚本系统 | `app.py`，保留传统 Ask 模式的洪水制图能力 |

所以这个仓库不是“新代码替换旧代码”，而是**新旧两条能力线并存**。

| 能力线 | 组成 |
|---|---|
| `Basic / Legacy` | Flask + 传统控件 + 固定图层分析 |
| `Advanced / Agent` | FastAPI + LangGraph + CopilotKit + 动态 AOI / 数据集推荐 |

你可以把它理解成两条请求路径：

1. 旧路径：前端直接调 Flask，做传统洪水图层分析。
2. 新路径：前端通过 CopilotKit 把对话交给 FastAPI Agent，再由 Agent 调 GEE 和数据集推荐逻辑。

## 4. 项目当前的主线问题

这个项目现在最关键的，不是再堆一个新功能，而是**收口系统边界**。

从代码现状看，主线已经很清楚。

### 4.1 AOI 输入正在从“散装字段”收口成标准对象

过去常见的 AOI 表达方式包括 `AoI_cords`、`bounds`、`geojson`、地点名加 buffer，以及 fishnet 选区。

现在项目正在往统一 AOI 结构上收口。前后端都已经出现同一个趋势：

- 后端：[`agent/flood_aoi.py`](E:\GMS\Flood\SatGPT-app\agent\flood_aoi.py)
- 前端：[`frontend/src/utils/aoi.js`](E:\GMS\Flood\SatGPT-app\frontend\src\utils\aoi.js)

标准 AOI 的核心字段大致是：

```json
{
  "version": 1,
  "source": "upload|draw|resolved|...",
  "label": "Chiang Mai flood boundary",
  "kind": "polygon|multipolygon",
  "bounds": {
    "west": 0,
    "south": 0,
    "east": 0,
    "north": 0
  },
  "geojson": { "type": "Feature", "geometry": {} },
  "legacy": {
    "AoI_cords": []
  }
}
```

这一步很关键。因为 AOI 在这个项目里相当于“准星”，准星不统一，后面所有图层请求、影响评估、GEE 导出都会偏。

### 4.2 数据集选择正在从“写死在代码里”收口成“注册表 + catalog”

当前新线的另一个主动作是把洪水相关数据集做成可维护的精选资产表：

- 注册表：[`agent/config/flood_dataset_registry.json`](E:\GMS\Flood\SatGPT-app\agent\config\flood_dataset_registry.json)
- 服务层：[`agent/flood_dataset_service.py`](E:\GMS\Flood\SatGPT-app\agent\flood_dataset_service.py)
- 下游 catalog 缓存：`experiments/water_asset_agent/cache/*.json`

这意味着项目正在从“每条链路自己决定用什么图层”，转向：

```text
精选注册表 -> 推荐上下文 -> 图层渲染 -> 前端展示
```

这个演化方向是对的。因为它把“业务流程怎么跑”和“具体跑什么数据”拆开了。

## 5. 第一次启动项目时要知道的事

### 5.1 默认端口

| 服务 | 端口 | 说明 |
|---|---:|---|
| React Frontend | `3000` | 用户可见界面 |
| CopilotKit Runtime | `5000` | 前端与 Python Agent 之间的桥 |
| Flask Backend | `5001` | 旧版 Ask 模式接口 |
| FastAPI Agent | `8000` | 新版 Agent 模式接口 |

### 5.2 一键启动脚本

主入口是 [`start_all.bat`](E:\GMS\Flood\SatGPT-app\start_all.bat)。

这个脚本按顺序启动 Flask、FastAPI Agent、CopilotKit Runtime、React Frontend。

另外还有 [`start_agent_layer.bat`](E:\GMS\Flood\SatGPT-app\start_agent_layer.bat)。

它更偏向 worktree / 分支开发场景，适合并行调试 Agent 线。

### 5.3 环境变量

参考 [`.env.example`](E:\GMS\Flood\SatGPT-app\.env.example)。

最关键的环境变量如下：

| 类别 | 关键变量 |
|---|---|
| OpenAI | `OPENAI_API_KEY`、`OPENAI_API_BASE`、`LLM_MODEL` |
| 搜索 | `TAVILY_API_KEY` |
| GEE | `GOOGLE_APPLICATION_CREDENTIALS`、`GEE_PROJECT_ID` |
| 前端地图 | `REACT_APP_MAPBOX_ACCESS_KEY` |

如果 GEE 没配好，新线和旧线很多能力都会变成“前端能点，后端不出图”。

## 7. 当前系统的几个关键判断

### 7.1 这是“双轨制”，不是“一套代码”

如果你看到两套接口、两套图层逻辑、两套 UI，不要慌。那不是纯粹历史包袱，而是项目阶段性现实：旧链路负责稳定可用，新链路负责智能化、标准化和未来扩展。

### 7.2 新线的核心增量，不只是“加了 Agent”

真正有价值的不是聊天框，而是 AOI 标准化和数据集选择标准化。

聊天只是入口，真正决定项目能否持续演进的是这两个中间层。

### 7.3 旧线暂时不能粗暴删除

因为旧线仍承载基础分析能力，前端仍保留 Ask 模式，而 [`frontend/src/config/layerCatalog.json`](E:\GMS\Flood\SatGPT-app\frontend\src\config\layerCatalog.json) 和 [`app.py`](E:\GMS\Flood\SatGPT-app\app.py) 仍是一套稳定链路。

所以当前更合理的策略不是“推平重写”，而是**边收口边替换**。

## 8. 当前最值得警惕的坑

### 8.1 AOI 口径不一致

这是最危险的坑。因为它会造成一种很隐蔽的错误：

```text
地图看着对
但统计范围错了
最终报告也跟着错
```

### 8.2 图层配置分散

目前图层配置至少存在两套来源：

- 旧线：[`frontend/src/config/layerCatalog.json`](E:\GMS\Flood\SatGPT-app\frontend\src\config\layerCatalog.json)
- 新线：[`agent/config/flood_dataset_registry.json`](E:\GMS\Flood\SatGPT-app\agent\config\flood_dataset_registry.json) + `flood_dataset_service.py`

这不是 bug，但它意味着你改数据源时必须先判断自己在改哪条链路。

### 8.3 GEE 成功不等于前端一定能显示

因为前端地图层还要经过 tile URL 生命周期、Mapbox source / layer 注册，以及加载失败和超时处理。

这部分逻辑主要在 [`frontend/src/components/MapContainer.js`](E:\GMS\Flood\SatGPT-app\frontend\src\components\MapContainer.js)。

## 10. 一句话心智模型

**这个项目的主任务，不再是“再做一个洪水功能”，而是把“事件理解 -> AOI 归一化 -> 数据集推荐 -> GEE 计算 -> 地图展示 -> 代码/报告导出”这条链条稳定下来。**

只要抓住这条主线，很多文件就不再杂乱，它们只是这条流水线上的不同工位。
